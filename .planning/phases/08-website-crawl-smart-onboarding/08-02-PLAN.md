### Backend API contract (from 08-01)

- `POST /api/v1/onboarding/crawl` — `{url}` → `{profile, warning?}`
- `GET /api/v1/onboarding/profile` — `{profile}` or 404
- `PATCH /api/v1/onboarding/profile` — `{field: value, ...}` → `{profile}`
- `POST /api/v1/onboarding/profile/confirm` — `{profile}`

  <action>
  Add an `OnboardingCard` component in `src/main.jsx`. The component manages the onboarding flow as a single-card experience.

  **State:**
  - `urlInput` — the URL the merchant types.
  - `profile` — the profile object returned by the API (null initially).
  - `loading` — boolean for crawl-in-progress spinner.
  - `error` — warning/error message from crawl failures.
  - `onboardingStatus` — "idle" | "crawling" | "editing" | "confirmed".
  - `showReplaceWarning` — boolean for the re-fetch confirmation dialog (D-13).
  - `editedFields` — local edits before save, merged with profile.

  **Behavior:**
  1. On mount, call `loadOnboardingProfile()`. If a profile exists and is confirmed, set `onboardingStatus = "confirmed"`. If draft, show the editable card pre-filled. If 404, show the URL input.
  2. URL input + "Fetch" button: calls `crawlWebsite(url)`. Shows a loading spinner. On success, populates the editable card with the returned profile. If a draft profile already exists and the URL differs, show a warning dialog first (D-13).
  3. Editable card: all profile fields as form inputs (text, textarea, color, select). Edits update local state. A "Save Changes" action calls `updateOnboardingProfile(editedFields)`.
  4. "Confirm Profile" button at the bottom: calls `confirmOnboardingProfile()`. On success, hide the onboarding card and show the normal workspace.
  5. On crawl error: show whatever partial profile was returned, display a warning banner ("We couldn't fully analyze your website. Fill in the missing fields manually."), and let the merchant complete the form.

  **Integration with AppDemo:**
  - Add an `onboardingProfile` state to `AppDemo` (or check via API on mount).
  - When the merchant has no confirmed profile, render `<OnboardingCard />` instead of (or above) the normal workspace modules.
  - After confirmation, transition to the normal workspace view.
  - Dev-login / demo merchants can skip onboarding or see the card with a sample pre-filled profile.

  **Accessibility:**
  - Form labels for all inputs.
  - Loading spinner has `aria-label="Loading"`.
  - Color inputs support both text hex input and native color picker.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend profile data → UI | Profile data from the API is already sanitized server-side; render as text content, not innerHTML |
| user edits → PATCH API | Field updates are sent as JSON; server validates and sanitizes |
| URL input → crawl API | URL is passed to the backend; the frontend does basic format validation before sending |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-02-01 | Tampering | profile display | mitigate | Render all profile values as React text content (not dangerouslySetInnerHTML); server sanitizes on storage |
| T-08-02-02 | Spoofing | URL input | mitigate | Basic URL format validation in the frontend; backend performs full validation and fetch |
| T-08-02-03 | Information Disclosure | raw extraction | accept | raw_extraction_json is not included in the serialized profile response; frontend never sees it |
</threat_model>
