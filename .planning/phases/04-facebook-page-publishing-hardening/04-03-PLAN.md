<objective>
Replace the in-memory `_PAGE_TOKENS` dict with durable, encrypted SQLite persistence wired through the existing `token_boundary` abstraction, keeping the current vault API working so existing OAuth/publisher code and tests keep functioning.

Purpose: D-01 (encrypted SQLite table, ciphertext only), D-02 (persist redacted ref + credential fingerprint + rotation through `token_boundary`), D-06 (persist expiry/issued-at + reconnect_required state), D-07 (key per merchant/connected_channel/page). Today tokens vanish on restart and the path is plaintext.
Output: new `facebook_page_tokens` table + store helpers, an encrypted-vault rewrite of `facebook_token_vault.py`, and extended tests proving ciphertext-only persistence and dev fallback.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Graph payload → token store | Page access tokens (high-value secrets) cross into persistence; must be encrypted at rest |
| token store → client serialization | Only redacted boundary refs may leave the backend; tokens must never serialize |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | `facebook_page_tokens.ciphertext`, `list_connected_pages` | mitigate | Store Fernet ciphertext only (D-01); list/serialize via `serialize_token_boundary_ref` — no token column or token field; test asserts raw DB dump excludes plaintext |
| T-04-02 | Elevation of Privilege | vault no-key path | mitigate | D-05 dev fallback is in-memory + logged insecure; production fail-closed enforced upstream by `token_crypto` (04-01) |
| T-04-R | Repudiation | token rotation/expiry | mitigate | Persist `issued_at`/`token_expires_at` + token_boundary rotation metadata (D-06) for audit |
| T-04-SC | Tampering | dependencies | accept | No new installs in this plan (`cryptography` gated in 04-01) |
</threat_model>
