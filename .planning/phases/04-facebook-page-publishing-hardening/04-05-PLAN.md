<objective>
Add a capability/permission health layer so the merchant can see whether the selected Facebook Page can publish before jobs are allowed, and so the publisher refuses to create a job for a Page that is not in a publishable state.

Purpose: ACCT-03 (verify the selected Page has required publishing capability before publish jobs are allowed) and D-11 (surface connected / missing_permission / reconnect_required and block publish when not connected). Reuses the existing failure classification (FB-05) for invalidation detection.
Output: a `page_health` derivation in `facebook_oauth.py`, health surfaced in `connection_status()`, a pre-publish capability gate in `facebook_publisher.queue_facebook_publish`, and 190→`reconnect_required` marking.
</objective>

Existing seams: `connection_status()` returns `{status, configured, scopes, connectedPages, redirectUri}`. After 04-03/04-04, `facebook_token_vault.list_connected_pages(conn=...)` returns rows with `pageId, name, link, category, tasks, status, isActive` (no token). `facebook_publisher.queue_facebook_publish(conn, approval_id, payload, ...)` is the single entry for live publishing; it currently validates `page_id` is numeric, then calls `store.create_publish_job`. `classify_error_class(status, provider_error)` already maps Graph errors (401/403→authentication/missing_permission, etc). Facebook capability is indicated by the Page `tasks` array including `CREATE_CONTENT` (and/or `MANAGE`).

Health state contract (consumed by UI-SPEC 04-08 badges):
- `connected` — active Page, token present, `tasks` includes `CREATE_CONTENT`/`MANAGE`, status active.
- `missing_permission` — token present but tasks lack create/manage capability (pages_manage_posts not effectively granted).
- `reconnect_required` — no active token, or row status == reconnect_required (set after a 190/auth failure).
</context>
