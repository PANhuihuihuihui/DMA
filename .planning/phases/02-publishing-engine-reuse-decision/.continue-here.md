# Phase 02 Pickup: Publishing Engine Reuse Decision

<current_state>
Phase 01 is complete and fully gated. The backend publishing foundation, approval snapshots, fake publish lifecycle, retry/idempotency, debug diagnostics, storage boundary, build, and packaging checks all passed on the live tree.

Phase 02 is now the next roadmap step. Its purpose is to decide whether LocalPilot should wrap Postiz-style publishing infrastructure or use native provider adapters before any deep Facebook or TikTok request wrappers are built.
</current_state>

<carry_forward>
What Phase 02 must inherit from Phase 01:
- Publish-critical workflow records remain backend-owned.
- Browser localStorage stays limited to allowlisted preferences only.
- Debug and retry behavior must remain read-only/redacted on support surfaces.
- AutoCLI/browser-session automation is not allowed for production merchant publishing.
- Facebook remains the first production channel; TikTok remains second.
</carry_forward>

<phase_02_goal>
Make a clear reuse decision before deeper provider work begins.

Success for this phase means:
- The team can run a focused spike against a `PublishingProvider` contract.
- The spike records whether Postiz-style tooling can connect Facebook Pages, handle TikTok upload/post flows, submit media, return status, expose errors, and fit licensing/deployment needs.
- A documented go/no-go decision selects Postiz-style wrapping or native provider adapters.
- Production publishing paths explicitly reject scraping, cookie posting, and browser-session automation.
</phase_02_goal>
